# 登录：只发生在 Harbor 主机

## 结论

**别人用 Harbor 时，登录走 Harbor 自己的入口（Web 前端弹窗 / CLI），并且必须发生在 Harbor 进程所在的那台机器上。**

模型、豆包工作、Claude、Cursor 这类 AI 客户端**不负责登录**，也不应该接触账号密码或验证码。它们只调用 Harbor 的接口，发现未登录就停下来让人接管。

## 最快路径：首次使用向导

打开 Web 或桌面端，首启会自动进「开始使用」：

1. 填档案名、勾选要接入的平台（15 个适配器都可选，都会生成个人 SOP；向导默认只勾推荐 4 个），生成 `profiles/<name>/`；
2. 在「登录平台」步骤逐个点「去登录」，浏览器在这台机器上弹出；
3. 复制 MCP 配置到 AI 客户端。AI 登录后先调 `get_platform_skill(platform)`，拿该平台的 SOP 再发布。

已有档案不用重建：在「登录平台」步骤点「添加平台」，或跑
`uv run python -m cli add-platforms --name <name> --platforms bilibili,toutiao`。
它只追加平台并补 SOP，账号和主线不会被重写。向导只是把 CLI 的动作图形化，登录仍然发生在 Harbor 主机。

## 登录之后：所有管理项都能在界面调

登录只是开始。Harbor 把原来要手改文件的设置搬进了「设置」：

- **平台账号 → 配置凭据**：API 平台（博客园、自建博客、51CTO、Dev.to、GitHub Pages、公众号、Telegraph）点卡片上的「配置凭据」，表单直填、保存后自动检测。密钥只回显掩码；不用再手改 `config.json`。
- **内容档案 → 档案与策略**：主线、写作口吻、避免写法、最少配图/代码块、每日互动额度、活跃时间窗、时区都能改；完整字段（`accounts` / `content_plan`）走「高级 YAML」。
- **内容档案 → 平台与个人 SOP**：15 份 SOP 可逐份查看、按自己习惯改、恢复模板；改过的标「自定义」，不会被自检误报为漂移。平台也能从当前档案移除，或追加新平台。
- **多档案**：一台机器可以建多份内容档案（技术号/生活号），切换后 AI 读到的 SOP 跟着切；账号登录态与发布记录共用。
- **发布轨 / 发布中心 / 任务中心**：选平台、分类、知乎问题链接、草稿/直发、全自动/中断改配置/全手动、AI 声明、限流解除、人工任务继续/放弃、失败重试都在界面里。

## 三种部署形态

### 1. 本机 / 桌面版（推荐给个人）

Harbor 和浏览器都在你自己的电脑上。点「设置 → 平台账号 → 登录」或跑：

```bash
cd backed
uv run python -m cli --headed login --platform zhihu
```

弹出一个有头 Chromium，你扫码或输密码，cookie 落进 Harbor 的 `accounts.profile_dir` 和 cookie 快照。之后发布都用这份登录态。

### 2. 局域网 / 自己的服务器（有桌面）

Harbor 跑在服务器上，登录仍要在服务器那台机器弹出浏览器：

- 有桌面环境：直接在服务器上点登录；
- 无桌面但有 X：SSH `-X` 转发，或在服务器上开 VNC；
- 只开给本人：Web 端口用 SSH 隧道访问，不要直接暴露公网。

### 3. 公网云服务器（无显示器）

两种做法，按安全优先级：

1. **Xvfb + x11vnc / noVNC**：把 Harbor 的有头浏览器窗口映射到浏览器里，本人连上去完成扫码。登录态留在服务器。
2. **同机迁移数据目录**：在一台有桌面的机器上登录，然后把整个 data 目录（`accounts` 表 + `profiles/` + cookie 快照）搬到服务器。**只适合同一账号、同一出口 IP 的迁移**，跨地区/跨设备不保证平台不踢。

不要做的事：在模型客户端自己的浏览器里登录，再把 cookie 导给 Harbor。

## 为什么不能让模型登录

1. **Cookie 绑定浏览器身份**：profile、UA、指纹、IP 任一变化都可能触发平台风控。模型浏览器登录出来的 cookie 搬到 Harbor 的 Patchright profile 里，大概率被判异常。
2. **凭证不该进模型上下文**：密码、短信码、扫码确认一旦经过第三方 AI 服务，就等于把账号控制权交出去。Harbor 的设计是凭证只留在本机 profile。
3. **登录态是资产**：`accounts.profile_dir` + cookie 快照 + `waiting_human` 状态机，是 Harbor 能"断点恢复"的前提。它必须由持有这台机器的人控制。

## Agent 的正确角色

- 查状态：调 `GET /api/v1/hub/accounts/{platform}/check`（或 MCP 的会话工具），只看登录/离线，不碰凭证。
- 发起登录：提交 `login` 任务，由 Harbor 在有头浏览器里等人操作；Agent 不代为输入。
- 遇阻：任务进入 `waiting_human` / `pending_user`，前端提示"请接管登录"；登录完成后 `resume`，不要重试、不要猜密码。
- 发布前：先检查登录态；未登录直接报告，不要连续重试触发风控。

## 远程部署的最小要求

| 要求 | 原因 |
|---|---|
| Harbor 服务与浏览器同一台机器 | Cookie 在本地 profile，跨机拿不走 |
| `profiles/` 与 data 目录持久化（挂卷） | 容器重建不丢登录态 |
| Web 端口只给本人（SSH 隧道 / VPN） | 登录页等于账号入口，不能公网裸奔 |
| 一台机器一个用户 | 发布依赖个人登录态，多租户是负债；多档案只是不同内容策略，不是多用户 |

## 一句话给用户

装在自己电脑上 → 点登录 → 扫码 → 之后定时任务和 AI 都只是"用"这份登录态，不碰账号。
